# Целевая архитектура

## Продуктовый инвариант

Пользователь проходит весь путь без дизайнера, оператора и ручной проверки:

`загрузка → настройка → автоматическая проверка → генерация → автоматический QA → результат → скачивание или автоматическая доработка`.

Сервис создаёт концепцию фасада, а не строительный проект. Геометрия, этажность, окна, двери и кровля сохраняются, пока пользователь явно не разрешил конкретное изменение.

## Компоненты

| Компонент | Ответственность |
|---|---|
| Web app | загрузка, настройки фасада, согласия на изменения, прогресс, результаты |
| Public API | авторизация, валидация, idempotency, выдача signed upload/download URL |
| Object storage | оригиналы, нормализованные изображения, варианты и QA-артефакты |
| PostgreSQL | пользователи, проекты, задания, статусы, настройки, кредиты и платежные события |
| Queue + workers | проверка, генерация, QA, retries и доработки вне HTTP-запроса |
| Photo QA | пригодность исходника и понятное автоматическое решение: принять или запросить новое фото |
| Generation adapter | вызов выбранного image-to-image/control провайдера с сохранением структуры |
| Geometry QA | сравнение исходника и результата: контуры, этажи, окна, двери, кровля |
| Result service | версии, превью, скачивание и автоматическая доработка |
| Observability | correlation ID, структурированные логи, метрики, алерты и аудит событий |

## Статусная модель без ручной ветки

Допустимые классы состояний:

- `photo_validation_queued`
- `photo_retake_required`
- `configuration_required`
- `generation_queued`
- `generating`
- `qa_queued`
- `qa_failed_retrying`
- `ready`
- `revision_queued`
- `failed_terminal`

Нельзя использовать `manual_review`, `operator_pending` или состояния, требующие решения специалиста. Пограничный результат обязан либо автоматически повториться по формализованной стратегии, либо запросить у пользователя другое фото/настройку с понятным объяснением.

## Сохранение геометрии

Каждая настройка должна иметь отдельное разрешение:

- отделка стен;
- цвет и материал;
- цоколь;
- декоративные элементы;
- изменение кровли;
- изменение окон/дверей;
- конструктивные изменения.

Последние три категории по умолчанию запрещены. Generation worker получает immutable policy snapshot. Geometry QA сравнивает исходник с каждым вариантом и отклоняет результат при превышении порогов. Не прошедший QA результат пользователю не показывается.

## Надёжность и безопасность

- прямые загрузки в объектное хранилище по короткоживущим signed URL;
- server-side проверка размера, типа и фактического декодирования;
- шифрование in transit и at rest;
- секреты только в secret manager/VPS environment, не в Git;
- idempotency keys для создания проекта, оплаты и постановки заданий;
- ограниченные retries с backoff и dead-letter состоянием;
- webhook signature verification для платежей;
- retention и удаление оригиналов/результатов по политике;
- резервное копирование PostgreSQL и проверка восстановления;
- никакого долгого AI-вызова внутри публичного HTTP-запроса.

## Deployment

На переходном этапе GitHub Pages может остаться публичным фронтендом, а API — на VPS. До появления авторизации допустимо сохранить эту схему. Перед production-автоматизацией требуется:

- единый управляемый API-домен;
- CI для фронтенда и сервера;
- воспроизводимый VPS deployment или контейнерный runtime;
- health/readiness endpoints;
- секреты вне репозитория;
- отдельные development/staging/production окружения.

Выбор PostgreSQL, очереди, object storage, генератора, платежного провайдера и auth-провайдера выполняется в соответствующем этапе по официальной документации и не фиксируется этим аудитом.
