# Выбор платёжного провайдера для ВИЖУФАСАД

Дата последней проверки: 22 августа 2026 года.

## Исходные условия

- владелец зарегистрирован как самозанятый плательщик НПД без ИП;
- продукт продаёт цифровую услугу визуализации фасада российским физическим лицам;
- стоимость и кредиты определяет сервер по действующей версии тарифа;
- карты и платёжные реквизиты не должны попадать в инфраструктуру ВИЖУФАСАД;
- серверное подтверждение оплаты должно иметь проверяемую подпись;
- подписка допустима только после отдельного юридического и технического подтверждения.

Это техническое обоснование интеграции, а не юридическая консультация. Перед боевым включением владелец подтверждает допустимость вида деятельности для НПД, реквизиты продавца и договор с провайдером.

## Сравнение

| Критерий | Robokassa | ЮKassa |
|---|---|---|
| Самозанятый без ИП | Поддерживается; официальный сценарий предлагает получить статус НПД, зарегистрироваться и активировать магазин | Поддерживается; на официальном сайте есть отдельное решение для самозанятых |
| Способы оплаты | Карты РФ, СБП, SberPay, T-Pay, Mir Pay и другие способы; конкретный набор зависит от договора | Карты, СБП, SberPay, ЮMoney и другие способы; конкретный набор зависит от договора |
| Чеки НПД | «Робочеки СМЗ» подключаются к «Мой налог», автоматически создают чек, передают его покупателю и ФНС | Доступны решения для чеков, но состав и тариф нужно подтверждать при подключении конкретного магазина |
| Webhook | `ResultURL` содержит `SignatureValue`; сервер обязан сверить подпись, сумму, номер счёта и пользовательские параметры | Официальная документация рекомендует проверить статус объекта повторным API-запросом или IP источника; отдельной криптографической подписи webhook нет |
| Идемпотентность | Реализуется магазином по `InvId` и внутреннему идентификатору платежа | API поддерживает ключи идемпотентности; webhook всё равно требует собственной защиты от дублей |
| Тестовый режим | Отдельные тестовые Password #1/#2 и `IsTest=1`; реального списания нет | Есть демонстрационный магазин и тестовые платёжные данные |
| Возвраты | API возврата принимает подписанный JWT с Password #3; требуется `OpKey`; поддерживаются полный и частичный возвраты | API поддерживает возвраты и их статусы |
| Рекуррентные платежи | Технически поддерживаются, но услуга доступна только по предварительному согласованию | Технически поддерживается сохранение способа оплаты и повторные платежи; доступность зависит от договора |
| Комиссия | Публикуется по способам и тарифным планам; базовые значения на сайте на дату проверки начинаются выше для карт, чем для СБП. Итоговую ставку фиксирует договор | Публикуется по способам; дополнительно указаны НДС с комиссии и возможная стоимость чекового решения. Итоговую ставку фиксирует договор |

## Решение

Основной провайдер этапа 11 — **Robokassa**. Причина: официальный сценарий для самозанятого НПД, автоматические «Робочеки СМЗ», российские способы оплаты, отдельный тестовый режим и подписанное серверное уведомление. Это напрямую выполняет требование проверять подпись webhook.

Резервный вариант — **ЮKassa**. Она остаётся подходящим коммерческим провайдером, но переход потребует заменить проверку `SignatureValue` на подтверждение статуса платежа через API плюс фильтрацию официальных IP. Без отдельного изменения критерия безопасности она не является взаимозаменяемой реализацией.

На 22 августа 2026 года владелец подтвердил статус самозанятого НПД, а магазин Robokassa с идентификатором `vizhufasad` имеет статус «Активен». Боевые Password #1/#2/#3 и персональные реквизиты хранятся только на VPS вне репозитория. Разовая production-оплата фактически подтверждена.

## Разрешённый объём этапа

- Включаются только разовые покупки пакетов кредитов.
- Plus создаётся как неактивная тарифная возможность, но не показывается и не продаётся.
- `FEATURE_SUBSCRIPTIONS_ENABLED=false` сохраняется до письменного/кабинетного подтверждения Robokassa о доступности рекуррентов конкретному магазину.
- JWS от `ResultUrl2` проверяется сертификатом с официального адреса Robokassa. Сертификат хранится отдельным файлом, его срок действия контролируется при развёртывании; URL и ключ включаются только парой.
- Redirect покупателя показывает только информационный статус и никогда не начисляет кредиты.
- Кредиты начисляет только обработка валидного `ResultURL` с совпавшими суммой, `InvId` и внутренним id платежа.
- Для возврата нужен `OpKey`. Основной путь — подписанный `ResultUrl2`; если уведомление не доставлено, сервер запрашивает состояние оплаченного счёта через официальный `OpStateExt`, подписанный Password #2.

## Измеренный staging-тест 9 августа 2026 года

- Тестовый магазин `vizhufasad`, режим `IsTest=1`, алгоритм `SHA256`.
- Счёт `InvId=100003`: пакет «Старт», 790 ₽, 25 кредитов.
- Robokassa показала успешную тестовую операцию без реального списания.
- `ResultURL` получен с официального адреса Robokassa, подпись, сумма, `InvId` и `Shp_payment` прошли проверку.
- Платёж перешёл в `paid`; создана ровно одна `purchase`-транзакция на 25 кредитов; баланс тестового кошелька стал 25.
- Повторная обработка и параллельный дубль покрыты интеграционным тестом; целевой payment-набор прошёл 14 из 14 тестов.
- Практический тест выявил особенность платёжной формы: `Receipt` передаётся двойным URL-кодированием, а `ResultUrl2`, `SuccessUrl2` и `FailUrl2` участвуют в SHA256-строке исходными значениями. Регрессионные тесты фиксируют этот формат.
- Возврат браузера получил `401` только из-за Basic Auth закрытого staging-сайта; серверное подтверждение и начисление выполнились до возврата браузера. В production эта staging-защита отсутствует.
- На момент контрольной проверки `ResultUrl2` не был доставлен, `OpKey` отсутствовал, а запись чека оставалась `pending`. До боевого включения требуется подтвердить активацию магазина, подключение «Робочеков СМЗ» и получение `ResultUrl2`; автоматический денежный возврат без `OpKey` не запускается.

## Production-проверка 22 августа 2026 года

- Магазин работает в основном режиме: `PAYMENT_TEST_MODE=false`, тестовый режим в production запрещён, Password #1/#2/#3 настроены вне репозитория.
- Для минимизации фактического списания применён одноразовый 99-процентный промокод. Счёт `InvId=100020` на 7,90 ₽ был реально оплачен через Robokassa.
- Валидный `ResultURL` обработан как `processed`; платёж перешёл в `paid`. Redirect пользователя не участвовал в подтверждении.
- В кошелёк начислено ровно 25 кредитов одной `purchase`-транзакцией; показанный пользователю баланс изменился с 1 до 26 кредитов.
- Подмена цены исключена: исходная цена, скидка и число кредитов рассчитаны сервером из PostgreSQL, браузер передал только идентификатор тарифа и промокод.
- Первые доставки `ResultUrl2` выявили несовпадение Content-Type и получили `400`; обработчик исправлен так, чтобы принимать компактный JWS независимо от MIME, сохраняя обязательную проверку RS256 и магазина.
- После прекращения повторов `ResultUrl2` сервер получил `OpKey` того же оплаченного счёта через официальный read-only `OpStateExt`. Состояние операции — `100`, ключ сохранён без вывода в логи.
- Возврат реализован через подписанный Password #3 JWT, идемпотентное резервирование, последующую сверку статуса и резервное получение `OpKey`. Реальный денежный возврат контрольного платежа не запускался, поскольку это отдельная финансовая операция.
- В истории создана запись чека со статусом `pending`: Robokassa и «Мой налог» формируют и отправляют чек вне `ResultURL`, а ссылка на чек в этом уведомлении не возвращается.
- Локально прошли `npm run check`, 20 из 20 целевых платёжных тестов и полный серверный набор 127 из 127. До последнего серверного изменения также прошли Next.js `typecheck` и production build.
- Подписки Plus остаются выключенными: `FEATURE_SUBSCRIPTIONS_ENABLED=false`. Разрешение на рекуррентные списания для магазина не подтверждено.
